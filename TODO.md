# Verity AI — Outcomes

- [x] **Landing page and responsive navigation** — The landing page presents VERITY, “DON'T JUST TRUST AI. VERIFY IT.” and “AI CAN BE CONFIDENT. BUT IS IT CORRECT?” with oversized black typography and vermilion emphasis; supporting copy explains investigation of AI-generated answers using live web evidence. Provide a multiline input with a 12,000-character maximum, counter, paste text, clear, try sample and INVESTIGATE controls. Show 01 EXTRACT / 02 VERIFY / 03 CORRECT. Include How It Works, claim extraction/live web intelligence/stale detection/evidence/source attribution/corrected answer features, a clearly labelled report preview, trust/transparency, “STOP GUESSING. START VERIFYING.” CTA and product/documentation/GitHub/about/contact footer links. Use compact accessible mobile navigation and avoid horizontal overflow.

- [x] **Verification workspace and backend API** — Users can paste or manually enter AI-generated text, load an example, clear text, see character count, and start verification through an actual backend request. Show the stages 01 extracting claims, 02 searching live sources, 03 collecting evidence, 04 evaluating claims, 05 generating report; only mark stages complete when supported by actual backend events/request state. Provide loading, empty and error states. Expose POST `/api/extract-claims`, POST `/api/verify`, POST `/api/correct`, GET `/api/history`, GET `/api/report/{report_id}`, DELETE `/api/report/{report_id}`, and GET `/health`; validate input, handle API errors and timeouts, and use async processing where appropriate.

- [x] **Evidence-backed verification engine** — Use Groq to extract independently verifiable claims, split compound statements, preserve meaning, add no new facts, categorize Historical/Technical/Pricing/Legal/Company/Current events/General, set Low/Medium/High temporal sensitivity, and generate targeted search queries. Use Tavily Search and where appropriate Extract to retrieve relevant preferably authoritative evidence, preserving title, URL, snippet/content, relevance score and available publication/update dates; avoid unnecessary duplicate searches. Use Groq to distinguish support, contradiction, conflict and insufficient evidence, with structured JSON validated by Pydantic. Verdicts are CURRENT (sufficient recent support), STALE (newer evidence indicates outdated), CONTRADICTED (credible direct disagreement), UNSUPPORTED (insufficient evidence), CONFLICTING (credible sources disagree), or STABLE (relatively timeless/historical claim remains supported). Assess freshness separately from confidence; use category, sensitivity, dates, temporal changes and newer contradictions; do not treat old source dates alone as stale, or present arbitrary percentages as scientific certainty. Explain uncertainty and generate an updated answer using supported evidence with citations/source links; do not fabricate missing information, source URLs or dates.

- [x] **Results dashboard and claim investigation** — Show VERIFICATION REPORT/report ID and total, current, stale, contradicted, unsupported and conflicting claim metrics. Provide split-screen original submitted answer and selected claim investigation. Highlight claims in distinct current/lime, stale/vermilion, contradicted/red, unsupported/yellow and conflicting/blue styles; selecting a highlighted claim updates the detail panel. Filters include All, Current, Stale, Contradicted, Unsupported and Conflicting; allow sorting by verdict and confidence. Selected claim detail includes original claim, verdict, category, temporal sensitivity, confidence assessment, freshness assessment, explanation, supporting/contradicting evidence, source links and available publication/update dates. Provide corrected-answer before/after comparison and copy action.

- [x] **Evidence Explorer and source transparency** — For each selected claim display original statement, search query, retrieved sources, title, domain, URL, relevant excerpt, available publication/update dates, and supporting/contradicting classification in structured comparison panels. Evidence panels can expand; original sources open in a new tab. Clearly distinguish retrieved evidence from LLM-generated explanation. Never invent source URLs or publication dates.

- [x] **History, persistence and export** — Persist reports in the initial SQLite implementation behind a database-access boundary that can later support PostgreSQL. History shows report ID, submitted-text preview, verification date, claim count, stale count and overall result summary. Provide search, filters, sorting, reopen report, delete with confirmation and PDF export. Copy report link only where a real route supports it.

- [x] **About, Settings, reliability and delivery docs** — Provide About/How It Works and Settings destinations and reusable components/design system. Use meaningful loading, empty and error states, accessible color contrast, responsive behavior, maintainable structure, README and deployment instructions. Keep a route manifest synchronized with all website pages. Never present hardcoded fake verification results as actual application data; mock data is allowed only in explicitly labelled previews/development testing. Keep Groq/Tavily credentials in backend environment variables and never expose them in React code.

- [ ] **Evaluation and tests** — Create an approximately 50–100 claim manually labelled benchmark containing current, stale, historical, contradicted, unsupported and conflicting claims. Evaluate precision, recall, F1-score, classification accuracy, average latency and cost per verification, and compare with a basic LLM-only baseline. Write unit tests for freshness and confidence calculations, integration tests for backend endpoints using pytest/HTTPX, and frontend component checks where appropriate.

  **Progress:** The 50-claim, six-verdict benchmark fixture, metric scorer, Groq-only baseline runner, freshness/confidence unit tests, API integration tests and production frontend type/build check are present; 11 backend/evaluation tests pass. Full prediction-based end-to-end metrics and the measured Groq-vs-baseline comparison remain pending because they require a benchmark run against the external providers.

- [x] **Groq rate-limit recovery** — When Groq returns HTTP 429, explain that the provider is rate-limiting the configured model/key, show a safe retry delay when the provider sends one, and clarify that Settings key-present status does not measure remaining quota. Do not make unbounded automatic calls; offer an explicit retry of the same submitted text and keep Settings guidance available without losing the input.

- [x] **Groq structured-output normalization** — In claim extraction, normalize a valid top-level claim array to the expected `{"claims": [...]}` object before Pydantic validation; continue rejecting malformed or schema-invalid content, never mark it verified, and test the normalization without external provider calls.

- [x] **Groq rate-limit resilience** — During an investigation, batch claim assessments to reduce provider calls, serialize and retry a transient Groq 429 once only when a safe bounded Retry-After is supplied, retain an actionable error when the provider quota is exhausted, and never mark an incomplete investigation verified.
  **Validation evidence:** 22 backend/evaluation tests pass, including one-call assessment batching and bounded Retry-After behavior; the frontend production build passes.
